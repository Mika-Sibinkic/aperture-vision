# Aperture: determinism layer

The vision model estimates weight from pixels. That will never be exact.
But several parts of the calculation are NOT stochastic; we can inject
deterministic code into the n8n workflow so the model only has to guess
the parts it actually needs to guess.

## What's deterministic vs. stochastic

| Stage | Deterministic? | Who owns it |
|---|---|---|
| ChArUco board pixels-per-inch calibration | YES | OpenCV would solve this exactly. gpt-4o estimates it; we can replace with OpenCV pre-processing later. |
| Detecting "is the item inside the yellow zone?" | YES (with OpenCV polygon test) | gpt-4o does it now. Replaceable. |
| Item classification (is it produce? canned goods?) | NO | Vision model |
| Volume from bounding box × stack height | Mixed: the shape detection is vision, the multiplication is deterministic | |
| Density lookup ("lbs per cu_in for red onions") | YES | Open Food Facts + our own table |
| Container tare subtraction | YES | `data/containers.json` |
| Bias correction from residuals | YES | `bias-table.json` |

## Layer 1: container tare subtraction

**Where**: `data/containers.json` (human-editable lookup).

**How it's wired in**:
1. Vision model is instructed to return an extra field `container_type`
   (already added to the prompt; see prompt v0.2)
2. The n8n workflow has a "Apply container tare" Code node that:
   - Reads `data/containers.json`
   - Matches the detected `container_type` against the `keywords` arrays
   - Subtracts `tare_lbs` from the model's raw `weight_lbs`
3. Both `weight_lbs_raw` (pre-tare) and `weight_lbs` (post-tare) are logged,
   so residuals can be computed honestly.

**How to extend**: when a new container shows up in the wild, edit
`data/containers.json` and add an entry. No code change needed.

## Layer 2: density priors (per item type)

**Important architectural note:** static lookup tables (Open Food Facts
global averages) are systematically wrong for Cul2vate's specific supply
chain. Tennessee-grown October red onions have different moisture content
+ density than California-grown March red onions. Same SKU, different mass
per cubic inch.

**The right model is LEARNED density per (item_type × season × supplier):**
each donation that gets a true_weight contributes
`true_weight / measured_volume` to the running mean per class. After 5+
samples in a class, the learned density REPLACES the prompt's static range.

**Status:** lookup tables are the v1 starting point only. Learned density
is on the v2 agenda; see `docs/V2-AGENDA.md` Item 3. Until ground-truth
capture is wired (V2-AGENDA Item 4), we run on lookup with the bias-table
multiplier as a coarse correction.

**File:** `data/learned-densities.json` (regenerated by training loop;
empty for v1; ignored when sample count per class < 5).

## Layer 3: bias table (residual correction)

**Where**: `public/bias-table.json` (regenerated by the training loop from
logged residuals).

After N real donations, the training loop:
1. Reads all logged donations where a "true" weight was recorded (when
   someone manually entered it as the source of truth)
2. Computes residual = (true_weight - predicted_weight) / predicted_weight
3. Aggregates per item_type class
4. Writes a multiplier per class, clamped to ±20% delta (anti-hallucination)
5. Redeploy Vercel → new bias table → n8n picks it up on next run

**How truth is collected**: two paths
- Ground truth from the scale: the dock has a platform scale visible
  in the camera view (orange/gray floor tile on left). If Cul2vate weighs
  the donation on that scale *after* the camera button press, we can add
  a second "Enter actual weight" button in a v2 UI that feeds the loop.
- Ground truth from Farmbrite: if the client contact edits the donation record in
  Farmbrite to correct the weight, we poll for those edits and treat them
  as truth.

Until ground truth is flowing, the bias table stays at `{}` and predictions
run raw. The system is still useful, just without the correction layer.

## Layer 4: ChArUco OpenCV pre-processing (future)

Currently gpt-4o estimates pixels-per-inch by "looking at" the ChArUco
board. For Phase 2, we'll pre-process the snapshot through OpenCV's
`aruco.detectMarkers` + `aruco.interpolateCornersCharuco` to compute
pixels-per-inch *exactly* before it reaches the model. Expected accuracy
improvement: single-digit percent.

Not blocking for launch; gpt-4o does this well enough with a clear
calibration board (which yours is).

## What you get in the Sheet

Every row now has both the raw and adjusted weights:

```
weight_lbs_raw        = what the model predicted
container_type        = what the model classified (e.g. "banana-box-standard")
tare_lbs              = looked up from containers.json
weight_lbs            = weight_lbs_raw - tare_lbs (this is what we report)
bias_multiplier       = from bias-table.json (1.0 if no correction yet)
weight_lbs_adjusted   = weight_lbs * bias_multiplier   (final user-facing)
confidence            = model's self-reported confidence
```

This gives you five channels of ground truth to debug with when a prediction
goes sideways.
