# Aperture v2: determinism maximization agenda

The v1 architecture (single gpt-4o call + lookup tables + post-hoc bias) is
shippable but leaves accuracy on the table. v2 redesigns the pipeline around
two principles:

1. **Geometry is solved, not guessed.** OpenCV does ChArUco math; vision
   models receive exact pixels-per-inch and a perspective-corrected image.
2. **Specialists beat generalists.** Each vision call answers exactly one
   question. The system's final answer is an ensemble vote with confidence
   derived from inter-model agreement.

## Items

### 1. ChArUco OpenCV preprocessor (FOUNDATIONAL)

**File:** `bridge/charuco_preprocessor.py` (runs on Dell G7 inside the bridge
service before returning the snapshot to n8n).

**What it does:**
- Receives raw JPEG from Hik-Connect
- Runs `cv2.aruco.detectMarkers` with the 6×7 board dictionary
- Runs `cv2.aruco.interpolateCornersCharuco` to get sub-pixel corner positions
- Computes homography matrix from the 4 outer board corners (known: 32"×40")
  to the camera image plane
- Returns:
  - The original JPEG
  - The perspective-corrected staging-zone crop (top-down view)
  - `pixels_per_inch_at_floor` (exact, derived from board geometry + assumed floor depth)
  - `homography_matrix_3x3`
  - `charuco_confidence` (function of: # markers detected, reprojection error)

**Bridge response shape:** instead of `image/jpeg`, returns
`multipart/related` with the JPEG + a JSON sidecar containing the geometry.
n8n unpacks both.

**Effort:** ~3 hours. OpenCV is already reliable; the math is textbook.

**Accuracy gain:** removes the single largest source of error in v1.
Estimated residual reduction: 8-15 percentage points.

### 2. Specialist ensemble (REPLACES the single vision call)

**Pipeline (replaces current `Vision: weight estimate` node):**

| Stage | Specialist | Input | Output | Model |
|---|---|---|---|---|
| 1a | Container classifier | Crop, geometry | `container_type` enum | Llama 3.2 11B Vision (NIM, free) |
| 1b | Food classifier | Crop | `food_type` enum + `confidence` | gpt-4o-mini |
| 1c | Prior-image retrieval | Crop embedding | `nearest_prior_id`, `similarity` | OpenAI text-embedding-3-large of CLIP features (or just CLIP cosine) |
| 2 | Volume estimator | Crop, geometry, food_type, container_type | `volume_cu_in`, `unit_count`, `avg_unit_size_cu_in`, `pct_container_fill` | gpt-4o (the heavy hitter, only invoked once) |
| 3 | Differential comparator | This crop, prior crop | `pct_fill_delta`, `unit_count_delta`, `unit_size_delta_pct` | gpt-4o-mini |
| 4 | Determinism engine | All above + learned_density + tare lookup + bias table | `weight_lbs`, `confidence_final`, `agreement_score` | Pure code, no model |

**Stages 1a, 1b, 1c run in parallel (one n8n branch each).**
Stage 2 runs after 1a + 1b complete.
Stage 3 runs after 2 + 1c complete.
Stage 4 is the final code node.

**Agreement scoring:**
- If volume estimator says 1500 cu_in but differential says "20% more than last
  similar donation which was 1200 cu_in" → predicts 1440 cu_in → high agreement
- If they disagree by >25% → confidence_final drops, row flagged
- If prior-image retrieval similarity is low (<0.6), differential is skipped
  and we report higher uncertainty bands

**Effort:** ~8 hours (4 new n8n nodes + agreement code + image storage layer).

**Accuracy gain:** estimated 5-10 percentage points on top of ChArUco fix.

### 3. Learned density (replaces static density priors)

**Where it currently lives:** static density ranges in the system prompt
(0.012-0.022 lb/cu_in for produce, etc.).

**Problem:** Tennessee-grown October red onions have different moisture
content + density than California-grown March red onions. Static = wrong.

**Replacement:** `data/learned-densities.json` regenerated by training loop:

```json
{
  "red onions": {
    "density_lbs_per_cu_in_mean": 0.0193,
    "density_lbs_per_cu_in_stddev": 0.0021,
    "n_samples": 14,
    "last_updated": "2026-04-22T...",
    "source_breakdown": {
      "october_2026": { "mean": 0.0188, "n": 8 },
      "march_2026":   { "mean": 0.0201, "n": 6 }
    }
  }
}
```

**How density is observed:** every donation that gets a true_weight (either
manually entered or via the platform scale capture in the camera FOV)
contributes `true_weight / measured_volume` to the per-class density mean.
After 5+ samples in a class, the learned density REPLACES the prompt's
static range. Below 5 samples, fall back to lookup with reduced confidence.

**Bonus:** track density per supplier (when known); eventually we can
auto-detect that "Sysco produce comes 8% heavier than ALDI produce" without
anyone telling us.

**Effort:** ~4 hours (training loop changes + density-fetch in workflow).

**Accuracy gain:** depends on regional bias magnitude; estimated 3-7 points.

### 4. Ground-truth capture (the missing input)

None of the above learns anything without ground truth. v1 has no path to
collect (image, true_weight) pairs. Three options:

**4a. Scale-in-frame OCR** (cheapest, automatic).
The camera already sees the platform scale's LCD display in the bottom-left
of frame. Add a 6th specialist: an OCR vision call that reads the scale
display when present. If LCD shows a stable reading within 5 seconds of
the button press, that's our true_weight.

Effort: ~2 hours. Bonus: zero human friction.

**4b. iPad correction button.**
After every donation, the iPad shows the predicted weight + an "Edit" link.
If the client contact/Joshua disagree, they tap, enter the real weight, and that becomes
ground truth for the residual loop.

Effort: ~3 hours (UI + n8n correction webhook + Sheet update).

**4c. Farmbrite reverse-poll.**
Periodically poll Farmbrite for inventory adjustments to records we
created. If someone edited the weight in Farmbrite, treat that as truth.

Effort: ~2 hours (Vercel cron job).

**Recommendation:** ship 4a first (zero friction), add 4b in v2.5.

---

### 5. Image storage layer (required for 1c + 3)

**Where:** Vercel Blob (1GB free tier, $0.15/GB after) or Cloudflare R2
(10GB free tier, better deal).

**What gets stored:** every snapshot, indexed by (timestamp, item_type,
container_type, weight_lbs_final). Retention: 90 days. After 90 days,
roll up to one representative image per (item_type × container_type)
combination + delete the rest.

**Why required:** prior-image retrieval (1c) and differential comparison
(3) both need access to recent past snapshots.

**Effort:** ~2 hours. Vercel Blob has a clean SDK.

## Phasing

| Phase | What ships | When |
|---|---|---|
| v1 (now) | Single gpt-4o call + static lookup + post-hoc bias multiplier | Tonight |
| v1.1 | ChArUco OpenCV preprocessor (Item 1) | Within 1 week; single biggest accuracy win, low risk |
| v1.2 | Image storage + scale OCR ground truth (5 + 4a) | Week 2; unlocks the residual loop |
| v2.0 | Full specialist ensemble (Item 2) | Week 3-4; once we have ground truth flowing to validate |
| v2.1 | Learned densities (Item 3) | Week 5+; needs ~14 days of v1.2 ground-truth data first |

**Why this order:**
- ChArUco fix needs zero ground truth and removes the biggest error source first
- Ensemble is meaningless without ground truth to compare against; it would just be more guesses averaged
- Learned density is meaningless without enough ground truth samples per class

## Estimated final accuracy (after v2.1)

| Stage | Typical residual |
|---|---|
| v1 (today) | ±15-25% |
| v1.1 (ChArUco fix) | ±10-18% |
| v2.0 (ensemble) | ±7-12% |

For comparison: a Cul2vate volunteer eyeballing the donation = ±20-40%.
A platform scale = ±2%. We will land between human eyeball and scale,
which is the right place for an automated system to live.
